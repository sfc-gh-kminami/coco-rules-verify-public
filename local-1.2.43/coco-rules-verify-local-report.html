1結論

読まれるのは5形式だけ

AGENTS.md・CLAUDE.md・CORTEX.md・RULES.md・.cursorrules。CLI のログにも、この5つのパターンだけを探していると出ています。

条件付きルールの仕組みはない

.mdc の globs、.instructions.md の applyTo、.claude/rules の paths は、どの操作をしても読み込まれませんでした（各 0/5）。

強制は hooks と --blocked

.cortex/settings.json の PreToolUse hook と --blocked は 5/5 でブロック。指示文だけの禁止も 5/5 守られましたが、仕組みで止めたわけではありません。

新しく分かったこと：v1.2.43 は git ルートより上のディレクトリの AGENTS.md も読みます（3階層上まで確認）。git 管理外のディレクトリでは作業ディレクトリだけ。サンドボックス版（v0.x-sandbox）は git ルートで止まっていました。
前提：測ったのは CLI だけです。条件付きルールや chat.instructionFilePatterns は CoCo Desktop のドキュメントの記述なので、「CLI で効かない」は「Desktop で効かない」という意味ではありません。

2どの形式が読まれるか

ルートに1形式だけ置いた空のリポジトリで、合言葉（ランダムな12文字）を答えられた回数です。

AGENTS.md5/5 CLAUDE.md5/5 CORTEX.md5/5 RULES.md5/5 .cursorrules5/5 SNOWFLAKE.md0/5 .cursor/rules/x.mdc0/5 .claude/rules/x.md0/5 TEAM.md（instructionFilePatterns）0/5

CLI ログで確認できる

~/.snowflake/cortex/logs/coco.log に次の行が出ます。どのファイルが読まれたかもここで分かります。

using patterns: ["AGENTS.md","CLAUDE.md","CORTEX.md","RULES.md",".cursorrules"]

そのほかの性質

  • ファイル名の大文字小文字は区別しない（agents.md・Claude.md・cortex.MD も各 5/5）
  • 12万文字のファイルも末尾の合言葉まで注入。スキップや警告はなし（約10万文字の上限は観測されず）
  • 読まれたファイルの観測ルール（末尾タグ）も各 5/5 で守られた

3どの場所が読まれるか

git 管理下（作業ディレクトリ = repo）

up/AGENTS.md             3階層上 → 読まれた
└── a/AGENTS.md          2階層上 → 読まれた
    └── b/AGENTS.md      1階層上 → 読まれた
        └── repo/       ← git ルート＆作業場所
            ├── AGENTS.md     読まれた
            ├── pkg-a/AGENTS.md pkg-a で起動時のみ
            ├── pkg-a/src/AGENTS.md
            └── docs/AGENTS.md
取り消し線 = 読まれない（docs 内を read しても 0/5）
上方向の追加ケースは 2/2、親の AGENTS.md は TC-W1 で 5/5

git 管理外・入れ子の git

# git 管理外（作業ディレクトリ = x/y）
nogit/AGENTS.md        読まれない
└── x/y/AGENTS.md     読まれた 2/2

# git の中に git（作業ディレクトリ = inner）
outer/  ← git
├── AGENTS.md         読まれた 2/2
└── inner/  ← git
    └── AGENTS.md     読まれた 2/2

読み方

  • 作業ディレクトリから上方向にだけ探す。下のディレクトリは読まない（後から読み込むこともしない）
  • git 管理下なら git ルートを越えて上まで探す（どこで止まるかは未確認）
  • git 管理外なら作業ディレクトリだけ
注意：ホームディレクトリの下にあるリポジトリで作業すると、~/AGENTS.md がユーザー指示とプロジェクト指示の両方として二重に入る可能性があります（未検証）。

4読み込み順と、矛盾したときの優先

ユーザースコープ4ファイルとワークスペース2ファイルを同時に置いたとき、6ファイルすべてが注入されました（5/5）。同名でもユーザー版はスキップされません。順序はログと回答（3/3）で一致しました。

1~/AGENTS.md
2~/CLAUDE.md
3~/.claude/CLAUDE.md
4~/.snowflake/cortex/AGENTS.md
5〜ワークスペース（上の階層から順。同じ階層ではドット始まり → アルファベット順）

矛盾したときはワークスペースが勝つ

ワークスペース「英語で答える」とユーザー（~/.snowflake/cortex/AGENTS.md）「日本語で答える」を同時に置くと、英語 5/5。

対照としてワークスペースの指示を外すと、日本語 5/5。後から入るワークスペース側が優先されています。

読まれないユーザースコープ

~/.claude/rules/u.md と ~/.cursor/rules/u.mdc は 0/5。ルールディレクトリはユーザー側でも読まれません。

5条件付きルール

対象ファイルを会話に入れるさまざまな操作を試しましたが、条件付きルールは一度も読み込まれませんでした。常時読まれる5ファイルは、すべての試行で注入されています。

TC操作対象ルール結果
TC-16@queries/sample.sql をメンションsql.mdc（globs: **/*.sql）、sql.instructions.md（applyTo）0/5
TC-17read ツールで .sql を読む同上0/5
TC-18write ツールで .sql を新規作成同上0/5
TC-21handler.ts を read して edit（編集は 5/5 成功）.claude/rules/api.md（paths: src/api/**/*.ts）0/5
TC-02何もしない（globs なしの .mdc、paths なしの .claude/rules）x.mdc、x.md0/5
実務での意味：CLI で「特定のファイルを触るときだけ効かせたい」内容は、ルールファイルではなく skills（description で自動的に呼ばれる手順書）に切り出すのが現実的です。

6強制：何で止められるか

ダミーの secret.txt を書き換えるよう依頼し、実行後にファイルのハッシュが変わったかで判定しました（bash 系は out.txt の作成で判定）。

陽性対照（制御なし）書換 3/3 AGENTS.md の指示文だけ防止 5/5 .cortex/settings.json hookブロック 5/5 .claude/settings.json hookブロック 5/5 ws の .snowflake/cortex/settings.json hook書換 5/5 matcher bash（小文字）ブロック 5/5 matcher Bash（大文字）ブロック 5/5 --blocked write,edit ＋ --allowed read防止 5/5
止まった（ファイル未変更）書き換えられた

指示文の 5/5 は「たまたま」

エージェントはツールを呼ばずに断っただけです。N=5 で破られなかったことは、仕組みとしての保証になりません。

hook に渡るツール名は先頭大文字

hook の呼び出し記録では Bash・Write。matcher は大文字でも小文字でも一致しました（docs の「小文字・大小区別あり」と異なる）。

--blocked は回避も防いだ

5回とも bash での書き換えを試みましたが、許可リスト外として拒否されました。

8推奨構成（CLI を前提）

用途おすすめ理由（今回の結果）
チーム共有の指示git ルートに AGENTS.md を1つ。CLAUDE.md を併用するなら @AGENTS.md だけにして内容を重複させない5形式は全部連結されるので、重複はトークンの無駄と矛盾の元になる
モノレポルートに共通、各パッケージに個別の AGENTS.md。パッケージを作業ディレクトリにして起動上方向にしか探さず、下位は読まれない
個人の指示~/.snowflake/cortex/AGENTS.md常に注入され、矛盾時はワークスペースが勝つ
リポジトリの外親ディレクトリに AGENTS.md を置きっぱなしにしないgit ルートより上も読まれる（v1.2.43）
条件付きにしたい内容skills に分ける.mdc・.instructions.md・.claude/rules は CLI で読まれない
必ず守らせたいこと.cortex/settings.json の PreToolUse hook（exit 2）。CI では --allowed / --blocked5/5 で決定的に止まった。指示文は保証にならない
使わない方がよいSNOWFLAKE.md、ワークスペースの .snowflake/cortex/settings.json（hooks 用）CLI では効かなかった

9方法と限界

方法

  • サンドボックス検証と同じハーネスを、パスだけ書き換えて使用（harness.py ほか）
  • 注入：各ファイルにランダムな合言葉を置き、ツールを使わせずに列挙させる。ツール結果から出た合言葉は除外
  • 遵守：ファイルごとの末尾タグや言語指定を出力から機械判定
  • 強制：ダミーファイルのハッシュ変化と、hook 側の呼び出し記録
  • 毎回新規セッション、モデル固定、メモリ・履歴・MCP 無効
  • ユーザースコープのファイルは一時作成して削除。前後のハッシュ一致を確認（match=true）。既存の settings.json・hooks.json は変更なし

限界

  • CLI のみ。Desktop（Instruction Files タブ、UI の Rules、条件付きルール）は未検証
  • git ルートより上の探索がどこで止まるかは未確認
  • compaction 後の指示の残存は未検証
  • 試行数は N=5（追加ケースは 2）。率ではなく件数で扱う
  • permissions.json とユーザーの hooks.json は、手元の設定を変えないため対象外

成果物

同じフォルダに report-local.md（本レポートの元）、results.jsonl（176試行の記録）、summary.txt（集計）、logs/（各試行の出力と CLI ログ）、env.txt、backup_restore.json があります。サンドボックス版のレポートは一つ上の coco-rules-verify-report.html です。
